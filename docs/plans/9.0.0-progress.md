## Approved decisions (do not revisit)

- Three packages, all 9.0.0: `LokiBulkDataProcessor.Core` (new), `LokiBulkDataProcessor` (same id, SQL Server provider on
  Microsoft.Data.SqlClient 6.1.8), `LokiBulkDataProcessor.Oracle` (new, Oracle.ManagedDataAccess.Core 23.26.400).
- Breaking changes allowed; each gets a README upgrade-guide row. Keep type forwarders for types that move to Core.
- `IBulkProcessorFactory`: injectable, mockable singleton, `Create(string providerName, string connectionString)`.
  Registration: `AddLokiBulkDataProcessor(...).AddSqlServer().AddOracle(...)`; the legacy `AddLokiBulkDataProcessor(connectionString, ...)` keeps working.
- No capability flags in the SPI: every provider joins the caller's transaction. Writers have a single `WriteAsync`.
  Oracle direct path is synchronous (document as an Oracle API limitation).
- Oracle options: `WriteMode` ArrayBind (default) / DirectPath (opt-in); `IdentifierResolution` Unquoted (default) /
  CatalogLookup (opt-in); `BooleanBinding` Number (default) / Boolean. Minimum Oracle 19c; tests on `gvenzl/oracle-free:23-slim-faststart`.
- `IBulkProcessor.ConnectionString` is removed. The SQL integration test project keeps the name `LokiBulkDataProcessor.IntegrationTests`.
- Direct-path hazards to document: FKs not enforced; a duplicate PK leaves the index UNUSABLE; tables with triggers are
  refused; one load per transaction; `EnforceIndexChecks` hung in testing, never use it.

## Notes / decisions

- Step 1: CI also triggers on `release/**` (not in the plan) so the step PRs get CI. `Version` is 9.0.0 from step 1.
- Environment (cloud container): install the SDK with `apt-get install -y dotnet-sdk-10.0`; start Docker with
  `dockerd &` and run Testcontainers with `TESTCONTAINERS_RYUK_DISABLED=true`.
- Step 2: the external-transaction type check lives in `LokiDbConnection.AdoptExternalTransaction` (runs on the first
  `SaveAsync`, not in the `Transaction` setter), so a wrong type throws `ArgumentException` before any database work and
  the caller's transaction is untouched. Step 4 moves it to `SqlServerBulkCopyProvider.AdoptExternalTransaction` unchanged.
  `ILokiDbConnection` (public, deleted in step 4) now takes `Microsoft.Data.SqlClient.SqlTransaction`. EF Core 10.0.0
  needs MDS ≥ 6.1.1, so the library's 6.1.8 unifies with it and the integration tests run on 6.1.8.
- Step 3: moved with `git mv` to `LokiBulkDataProcessor.Core/`: `IBulkProcessor`, `Mappings/**`, `DataReaders/**`,
  `Utils/**`, `Logging/**`, `Exceptions/**`, `Constants/DefaultConfigValues.cs`. Still in the SQL project until step 4:
  `BulkProcessor`, `Commands/**`, `Context/**`, `InternalDbOperations/**`, `Constants/DbConstants.cs`, DI extension.
  - Core has `InternalsVisibleTo` **`LokiBulkDataProcessor`** (the SQL assembly), UnitTests and IntegrationTests, because the
    commands still use Core internals (`ReflectionUtils`, `ThrowIf*` guards, `MappingInfo`, `DefaultConfigValues`,
    `JsonDataReader`). Step 4 should drop the Core → SQL IVT once the SQL provider only uses the public SPI (or keep it
    deliberately and record why).
  - `JsonDataReader` now takes a non-generic `ILogger` (it used to take `ILogger<BulkProcessor>`, which can't be named from
    Core yet). `BulkProcessor` still passes its own `ILogger<BulkProcessor>`, so the log category is unchanged.
  - Core references only `Microsoft.Extensions.Logging` for now. `FastMember` and `Microsoft.Extensions.DependencyInjection`
    stay on the SQL project; add `FastMember` and `DependencyInjection.Abstractions` to Core in step 4 when `BulkSource` and
    the builder land.
  - `Properties/AssemblyInfo.cs` is deleted (public empty `AssemblyInfo` class gone, IVT now csproj items, assembly version
    generated as 9.0.0.0). README upgrade-guide rows added for the move, the `AssemblyInfo` removal and #19.
  - `Properties/TypeForwards.cs` forwards the 10 types in the plan **plus** `IDataMappingCollection`,
    `IModelMappingCollection` and `AbstractMappings<T>`, which are still public here. Step 4 makes those three internal and
    must delete their forwarders in the same PR (forwarding to an internal type is pointless).
  - CI `unit` job checks both `LokiBulkDataProcessor.Core` and `LokiBulkDataProcessor` for Testcontainers.
  - Verified: `dotnet build -c Release` produces `LokiBulkDataProcessor.Core.9.0.0.nupkg` and `LokiBulkDataProcessor.9.0.0.nupkg`,
    the SQL nuspec depends on `LokiBulkDataProcessor.Core` 9.0.0, unit 45/45 and SQL integration 35/35 green locally.
  - **For step 9's `pack` job:** `dotnet pack LokiBulkDataProcessor -c Release` fails with NU5026 ("dll to be packed was not
    found") on a clean tree because `GeneratePackageOnBuild` is on. This already happens before step 3. Use
    `dotnet pack -p:GeneratePackageOnBuild=false` or `dotnet build -c Release` and collect the `.nupkg`s.
